01 · The architecture

A single codebase spans two execution environments.

The frontend and backend belong to the same Next.js project. They still execute in different places: browser JavaScript handles interaction; server-side Route Handlers execute trusted operations.

Browser: interaction and presentation

React displays orders and forms, keeps temporary selection state and sends requests to the same application's API. It never receives a database password.

src/components/return-form.tsx

How can the backend be “inside Next.js”?

A route.ts file under src/app/api/ exports a function such as POST. Next.js routes an HTTP request to that function on the server. The route calls the project's domain services; it is not browser code.

Vercel builds and runs the server side as Functions, while serving the interface and static files. “Fullstack” means both parts are delivered together; it does not mean SQL runs on the visitor's device.

Next.js: Route Handlers ↗ · Vercel: Next.js ↗

Why this architecture?

The constitution chooses a modular monolith for a small, demonstrable product. One repository keeps UI/API contracts together and avoids deploying and operating a separate backend service. The code still separates HTTP, domain rules and persistence.

The tradeoff is a shared release unit and dependence on the Functions runtime. The database remains an independent service, with its own capacity, connectivity and operational concerns.

          What happens when two requests arrive at the same time?
          
    
            The server resolves the visitor's environment and starts a database transaction. It
            locks that environment row before evaluating and changing its data. A competing
            operation for the same environment waits, then checks the updated quantities. PostgreSQL
            either commits the request, items, history and operation receipt together, or rolls them
            back together.
          
    
          
    
            An idempotency key distinguishes a retry of the same action from a deliberate new
            request. A matching successful retry reuses its recorded result; a changed payload with
            the same key conflicts. A generation check prevents an old tab from writing through a
            reset.

      Approval reserves; it does not pay.
      
            
      
              Approval applies to the whole request. The customer sees a simulated pickup within
              three business days and an explicit no-real-carrier explanation. Approval does not
              issue a refund or confirm physical receipt.
            
      
          
      
          
      
            
      Receipt is a separate decision.
      
            
      
              An administrator can confirm simulated receipt only after approval, without waiting
              three days. It ends the request and records a history event. Received quantities never
              become available for another return; no monetary refund is issued.
            
      
          
      
        
      
      
      
      
      
        
      
          04 · Independent demo environments
          
      Shared database. Scoped visitor data.
      
          
      
            A demo environment is a group of related records, not a separate Neon project, server,
            database or branch for every visitor.
          
      
        
      
        
      
          
      
            Browser A
            
      Customer tab ↔ Admin tab
      
            
      
              Tabs in the same browser profile share first-party cookies and the same persisted
              environment. Their selected role/customer stays in each tab's URL. After another tab
              makes a decision, Refresh loads the latest state.
            
      
          
      
          
      
            One PostgreSQL databaseEnvironment A → its orders / returns / historyEnvironment B → its orders / returns / historyServer queries enforce environment + generation scope
          
      
          
      
            Browser B
            
      Another visitor
      
            
      
              An independent browser profile/context receives a different visitor capability and
              environment. It cannot read or modify A's scoped resources. Product definitions are
              shared read-only catalog data.
            
      
          
      
        
      
        
      
          
      
            
      No login does not mean no checks.
      
            
      
              Server-issued HttpOnly cookies carry opaque capabilities. The server validates the
              visitor token, resolves the environment token hash, verifies ownership, generation and
              expiry, and enforces request origin and write limits. Database credentials stay on the
              server.
            
      
            
      
              These are anonymous demo capabilities, not authenticated people or business-role
              permissions. Anyone holding the same browser capability can switch between that demo's
              customer/admin views; this is not suitable authorization for a real store.
            
      
          
      
          
      
            
      Expiry and reset are different.
      
            
      
              After 168 hours of inactivity, access is refused and the visitor is offered an
              explicit fresh start. Merely reaching day seven does not silently reset the screen or
              data. A scheduled cleanup can remove expired records; access checks do not depend on
              that job running.
            
      
            
      
              A confirmed reset clears only this environment's generated history/requests and
              restores its initial data and 30-day policy. A generation change fences off stale
              writes from old tabs. The declared cleanup schedule is daily at 06:00 UTC; successful
              hosted job execution remains a release-verification item.
            
      
          
      
        
      
      
      
      
      
        
      
          05 · Know the tools
          
      Each technology has a specific job.
      
          
      
            Select a tool to see its responsibility in this repository. The API uses Node.js and
            Prisma/pg; it does not need an extra Express server or a browser-to-database connection.
          
      
        
      
        
      
          
      
          
      
            
            
      
            
      
            
        
            
        
          
        
        
        
        
        
          
        Neon, PostgreSQL and Prisma are different layers.
        
          
        
            PostgreSQL is the relational database engine.
            Neon operates the managed PostgreSQL service for this app.
            Prisma is the application library used to query it, backed by the pg
            driver. Vercel runs the Next.js application that makes those queries.
          
        
          
        
            Runtime uses a pooled connection; controlled migrations use a direct connection. Our
            production schema and ten-product catalog are already on Neon. Local/CI PostgreSQL is
            separate. Preview should get a separate database branch; that setup is still pending.
            Branches separate deployment environments, not individual demo visitors.
